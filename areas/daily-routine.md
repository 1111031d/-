# 経営者（k）の1日のリズム

この仕組みが「いつ」「どの場面で」読まれるかの前提。
プロンプトの締め切り・出力の粒度は、すべてこの時間割に合わせます。

## 朝のルーティン（目標として定めたもの）

| 時刻 | やること | この仕組みとの関係 |
|---|---|---|
| 5:30 | 起床 | **`/morning` を打つのはここ。** 打ったらすぐ散歩に出る（所要10秒） |
| 5:30〜6:00 | 散歩（30分） | Claude が裏で叩き台を生成している時間 |
| 6:00〜6:20 | HIIT | 同上 |
| **6:20〜6:50** | **1日のプランニング（30分）** | **★ここが成果物を読む時間。** この時点で叩き台が揃っている必要がある |
| 6:50〜7:45 | 子どもたちと朝食 | 仕事から離れる時間。ここに仕事を持ち込まない |
| 7:45 | 家を出る | |
| 8:05 | 事務所着 | |
| 8:05〜8:30 | 事務所内を整える | 手を動かす時間。判断は不要 |
| 8:30 | 業務開始 | |

## この時間割から導かれる設計上の制約

1. **成果物の締め切りは 7:30 ではなく「6:20」。**
   プランニングの30分が実際の読み込み・判断の時間です。
   `/morning` を5:30に打てば、生成に使える時間は**50分**あります。

2. **プランニングの30分で読み切れる量にする。**
   30分のうち、読むのは10分以内。残り20分はご自身が考える時間です。
   ターミナルに返す要約は「確認ポイント3つ＋判断待ち」だけに留め、
   本文はファイルに置いて、必要なときだけ開く形にします。

3. **朝食（6:50〜7:45）以降は仕事の判断をしない前提。**
   6:50までに判断が終わる構成にします。持ち越した判断は夜に回します。

4. **8:05〜8:30 は「手を動かす」時間。**
   ここに回せるのは、判断の要らない作業（撮影、写真のアップロード、
   Googleビジネスプロフィールの入力など）です。
   朝のプランニングで「この30分でやること」を1つ決める形が噛み合います。

## 夜のルーティン

**`/night`（3分）は「夕食後・子どもたちの就寝後」に置きます。**

- 家庭の時間を確保したうえで、落ち着いて1日を振り返れる時間帯です。
- 記憶がやや薄れる時間帯のため、思い出せることだけで構いません。
  整形も不要です。走り書き・音声入力のままで、仕分けはこちらで行います。
- **`/night` が入らないと、翌朝の叩き台は「前日に何があったか」を知らないまま作られ、
  一般論に寄ります。この仕組みの精度は、夜3分が入るかどうかでほぼ決まります。**
- **毎晩20:30にスマホへリマインドが届きます**（登録済み）。
  その日の `/night` が済んでいれば通知は出ません。

## 自動化の設定状況

| 何を | いつ | 状態 |
|---|---|---|
| `/morning`（叩き台の生成） | 毎朝5:30 JST | **自動実行を登録済み**（2026-09-03から稼働）。完了時にスマホへ通知 |
| `/night`（夜の入力） | 毎晩20:30 JST | **リマインドのみ自動**。入力そのものは手動（人にしかできないため） |

- 自動実行は毎日5:30に起動し、6:20のプランニングまでに `outputs/` を更新して push します。
- **特別な指示がある日だけ**、起床時に手で `/morning 今日は〜を優先して` と打ち直してください。
  自動生成された分とは別に、追加の叩き台が作られます。
- 20:30のリマインドは、その日の `inbox/<日付>.md` が未作成のときだけ通知します。
  未回答の「判断待ち」の件数と、期限の近いToDoを添えて届きます。
- 止めたいときは「朝5時半の自動実行を止めて」「夜のリマインドを止めて」と言えば解除します。
